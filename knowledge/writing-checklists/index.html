Как составить чек-лист по шаблону

После разбора ты сможешь оформить заданные проверки одной небольшой функции в короткий список и сгруппировать их по образцу. Полезные пререквизиты — классы эквивалентности и тест-кейс. Здесь условия и проверки даны: самостоятельно восстанавливать неполные требования не требуется.

Короткая запись должна оставаться проверяемой

Чек-лист помогает помнить, какие условия проверить. Каждый пункт должен допускать отдельную проверку; слишком общая запись оставляет исполнителю слишком много вариантов. Источник понятий — ISTQB CTFL v4.0.1, §4.4.3, с. 44–45.

«Проверить форму» не объясняет, какое поведение считать правильным. «При количестве 0 сообщение о диапазоне показано» уже задаёт конкретную проверку, если общие условия и точный текст сообщения доступны рядом. Краткость получается за счёт общих условий и ссылок, а не удаления смысла.

В нашем шаблоне один пункт соответствует одному отдельно отмечаемому результату. Действия и данные можно вынести в общую инструкцию, если они действительно одинаковы для всех пунктов. Это авторский формат упражнения, а не обязательный стандарт компаний.

Сначала задай общий контекст

Вымышленная форма записи на занятие принимает целое число мест от 1 до 8 включительно. Действие — кнопка «Записаться». Допустимое значение открывает подтверждение с тем же числом мест. Недопустимое показывает «Введите целое число мест от 1 до 8» и оставляет форму открытой.

Общие условия списка: тестовый стенд, остальные поля корректны, перед каждым пунктом открыта чистая форма без предыдущей ошибки. Для проверки вводится указанное число и нажимается «Записаться». Сборку и браузер исполнитель укажет перед реальным запуском; сейчас они неизвестны. Никакие проверки пока не выполнены.

Готовый набор данных для этого упражнения — 1, 8, 0 и 9. Это небольшой заданный срез, а не все классы ввода: пустая строка, дроби и буквы в этот список не включены. Сам чек-лист не объясняет и не доказывает полноту выбора данных; для этого нужна отдельная работа тест-дизайна.

Примени шаблон пункта

Используем запись: идентификатор — данные/условие — один наблюдаемый ожидаемый результат. Для каждого числа, если нужны разные независимо отмечаемые результаты, создадим отдельные пункты.

Позитивные проверки:

  • CL-01 — при 1 открыто подтверждение.
  • CL-02 — в подтверждении после ввода 1 указано 1 место.
  • CL-03 — при 8 открыто подтверждение.
  • CL-04 — в подтверждении после ввода 8 указано 8 мест.

Негативные проверки:

  • CL-05 — при 0 показано заданное сообщение диапазона.
  • CL-06 — при 0 форма остаётся открытой, перехода к подтверждению нет.
  • CL-07 — при 9 показано заданное сообщение диапазона.
  • CL-08 — при 9 форма остаётся открытой, перехода к подтверждению нет.

Эти восемь пунктов можно понять вместе с общими условиями. Если передать только «CL-05: ошибка», смысл потеряется. Сохраняй контекст при переносе списка в трекер.

Если для проверки текста подтверждение не открылось, не выдавай проверку текста за успешную: наблюдать его нельзя. Отметь причину по принятым правилам команды. Статус выполнения и ожидаемый результат — разные сведения.

Исправь составные и расплывчатые пункты

Запись «проверить 0 и 9, ошибки и переходы» объединяет несколько результатов. Один может оказаться правильным, другой нет — общей галочки уже недостаточно. Разделение помогает сохранить конкретное наблюдение без длинного комментария о частичном успехе.

Запись «интерфейс красивый» не даёт критерия. Нужны конкретное условие и основание: например, требование к видимости сообщения. Если такого требования не дали, сначала уточни его; не превращай личное предпочтение в дефект.

Группы тоже не являются результатами. Заголовок «Негативные проверки» организует список, но его нельзя отметить вместо всех пунктов. Не создавай пустые группы «Интеграции» и «Безопасность», если в упражнении таких проверок нет: это создаёт ложное впечатление покрытия.

Когда краткости недостаточно

Если исполнитель не знает, как получить нужное состояние, или последовательность действий существенно влияет на результат, добавь подробности либо ссылку на тест-кейс. Самостоятельный выбор формата для сложного проекта — отдельная задача; здесь достаточно увидеть ограничение короткой записи.

Не копируй один список без проверки в новую версию функции. Если максимум стал 10, ожидание ошибки для 9 устарело. Изменение требований требует пересмотреть данные и ожидания, а не только дату в шапке. Перед запуском убедись, что список относится к текущим правилам.

Попробуй по образцу

Для другой вымышленной формы дано правило: число участников — целое от 2 до 6. При «Далее» допустимое 2 открывает подтверждение с числом 2; недопустимое 7 показывает «Введите целое число участников от 2 до 6» без перехода. Начальное состояние и сброс — как в образце выше, прочие поля корректны.

Перепиши запись «проверить 2 и 7, всё правильно» в четыре отдельно отмечаемых пункта, сгруппируй их на позитивные и негативные. Числа уже выбраны; не требуется расширять покрытие. Укажи статус до запуска.

Показать разбор самопроверки

Один корректный ответ: позитивные — при 2 открывается подтверждение; после ввода 2 подтверждение показывает 2 участника. Негативные — при 7 показано заданное сообщение диапазона; при 7 перехода нет, форма остаётся открытой. Применяются общие действия и чистое начальное состояние. Все пункты до запуска «не выполнено»; это предложенный текст списка, а не результат исполнения.

Что оставить себе

Пункт должен быть понятен вместе с общим контекстом и иметь отдельно отмечаемый результат. Группы помогают найти проверку, а подробности обеспечивают повторение. Для найденного расхождения составь баг-репорт, сохранив данные и наблюдение.
